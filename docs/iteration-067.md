# Iteration 067 — 把外部验证任务收敛为一个真实进度工作台

## Before

- 诊断Gold、微练习审核和修复后用户复测分别有入口，但没有统一的实时下一步。
- 诊断启动页的静态邀请文字仍围绕首批10条；服务端实际已经10/50，容易误解为任务已经完成或需要重复前10条。
- 项目作者需要在多个页面和文档间判断当前进度，增加了错误执行和手工汇报不一致的风险。

## Change

- 新增`/validation.html`，并行读取`/api/reviews`、`/api/exercise-reviews`与`/api/usability-summary`。
- 工作台按证据门槛排序，只突出当前第一个未完成任务；现状自动显示为“10/50，继续下一批10条诊断教师盲审”。
- 三条证据轨道同时显示真实分子、门槛、剩余数量、协议入口和声明边界。
- 接口失败时不显示推测进度，而是明确要求检查服务后刷新。
- 页面沿用Reading Lens既有克制视觉系统，以“证据台账”而非通用Dashboard卡片呈现；桌面和390px移动视口均完成检查。

## After

- 当前页面权威显示：诊断Gold 10/50、微练习审核0/10、修复后复测0/3。
- 当前唯一主CTA指向诊断审核启动页；该页再依据服务端状态从CASE 11继续。
- 390px视口下`scrollWidth === clientWidth`，无横向溢出；动态进度和主CTA正确。

## Regression

- 工作台只读，不提交、修改或删除教师/用户记录。
- 不把作者QA、结构评测或首轮用户数据计入三个未完成门槛。
- 不改变学生核心流程或Provider。

## Next

- 外部执行动作是邀请合格独立教师完成CASE 11–20；保存后工作台将自动更新为20/50并继续指向下一批。
